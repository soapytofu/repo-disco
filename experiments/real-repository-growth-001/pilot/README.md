# Proposed sequential growth pilot

**At most eight new Claude calls, not authorized or executed.** The plan has two fresh lineages on each of the two qualified upstream projects, with at most two additions per lineage. Each stage gets one response, a protected body edit and a fresh full-scope native check. A rejected or unproved first addition blocks that lineage's child; its slot is never reassigned. Eight is a ceiling, not a target to fill.

| Project | First addition | Conditional second addition |
| --- | --- | --- |
| Dafny-VMC | Stable move to front at a valid sequence index, preserving length and multiset | Stable ordered selection of two indexed elements, using the actual accepted first addition as read-only context |
| Vest | Proof of a bounded U16-length-prefixed frame roundtrip with exact consumption and arbitrary suffix preservation | Recursive counted batch proof over the actual accepted frame API; payload order, total consumption and suffix preserved |

These are host-selected contracts on real pinned projects. Dafny adds sequence operations related to the existing Fisher–Yates model; Vest adds specification/proof library content, not executable parser generation. The batch count is supplied out of band. Direct child implementations are admissible. Calls to the prior API are recorded separately and do not establish necessary proof dependence.

## Why these tasks are ready to propose

The root `control-gates-001.json` binds the completed 11 Dafny and 12 Vest controls plus two previously reviewed full references. The controls check alternatives, insufficient implementations, failed parents with locally passing callers, and omitted additions. They are analyst controls, not generated repositories or accepted model parents. All original sources, contracts, trust assumptions, toolchains and full native coverage requirements remain protected.

The current pilot contains no accepted model-parent receipt and no exact stage-two payload. `protocol-003` supplies the separately reviewed actual-parent boundary; this proposal binds that reviewed runtime before freezing. A future execution handler and explicit paid approval are still required. Existing closed request ledgers and historical model results are not reused or rescored.

## Model-visible content

Four stage-specific templates contain the exact fixed target contracts/types/imports, a JSON `replacement` string instruction, a bounded grammar description and selected original upstream source files. Dafny receives the complete pinned `FisherYates/Model.dfy`; Vest receives 16 complete core/combinator/re-export files. Every selected file is hashed and copied without edits, with upstream licenses preserved. `context-selection.json` lists all selections and explicitly identifies omitted imports/transitive context. The visible context is not a complete dependency closure; the native verifier still checks the entire qualified declared scope.

The only display transformation removes an exact allowlist of leading template metadata comments about analyst authorship or stale verification status. `template-views.json` pins their positions and bytes. Imports, types, specification definitions, contracts, termination clauses, body markers and the batch count caveat remain unchanged. The candidate source retains its original protected bytes. The same narrowly defined view is derived from an actual accepted parent without altering its body; input and displayed hashes remain bound in the rendering record.

No new-growth reference/alternative solution, negative control, analyst repair advice, saved model response or initial failure feedback is included. Existing upstream API implementations are legitimate context. Stage two receives the actual accepted first addition, not the analyst reference. Native evidence and host receipts are validated and hashed outside the model-visible prompt.

## Proposed settings, order and budget

Settings are copied exactly from the published real-repository repair proposal: `global.anthropic.claude-opus-4-5-20251101-v1:0`, Bedrock Converse in `us-east-1`, temperature 1.0, at most 4,096 output tokens and one total SDK attempt. Availability has not been tested. The total proposed output ceiling is **32,768 tokens**.

The fixed order is Dafny first-stage 1, Vest first-stage 1, their conditional second stages, then Vest first-stage 2, Dafny first-stage 2, and their conditional second stages. Each slot starts a fresh model context. This reverses project order for the second pair of lineages; it is not a controlled language comparison or an independent-family evaluation.

The four first-stage payloads contain **336,822 serialized bytes** and **325,004 model-input characters**. Their exact sizes are recorded in `frozen-001/planned-sizes.json`. The worst-case all-eight input is **721,494 characters**, corresponding to a rough **144,299–240,498 input-token heuristic**. Stage-two payload size is bounded using the maximum admitted parent body but cannot be known exactly before acceptance. Dividing characters by 5 to 3 is only a planning heuristic, not tokenization, billing data or a provider measurement.

An ordinary guard or proof rejection is an evaluated failed stage and blocks its child. Provider ambiguity, integrity drift or unresolved native execution halts future dispatch, preserving evidence without retry, recovery or reassignment. No iterative feedback-repair loop is proposed. The future handler must bind every accepted parent to that lineage's exact first-stage request and source history.

## Frozen versus future-dependent material

`render.py` produces the four exact stage-one payloads and the four stage-specific templates deterministically. `build_freeze.py` refuses final construction until the reviewed `protocol-003` binding exists. Child entries carry a null payload and an explicit deferred status. `render_stage2` requires complete actual parent sources, a host-pinned accepted-parent binding and replayable native artifacts from the same lineage. It rejects synthetic, failed, stale, changed or analyst-reference parents by default.

The separately named synthetic renderer requires explicit test opt-in, labels its result ineligible for future dispatch and is used only in offline tests. Synthetic native rows and receipts are never live payload inputs, claimed model acceptances or proof observations. The initial preview directories are historical unapproved drafts, not frozen model execution scopes.

## Measurements and limits

The primary outcome is completion of both additions under full native verification in each of the four prespecified lineages. Report first-stage acceptance, conditional second-stage acceptance, blocked children, rejection categories, original/additional warnings, returned model tokens and native time/resource use separately. Undispatched children are not failed model responses, and an ambiguous provider request has no proof score.

Two task chains and two repetitions per project remain a small development feasibility study. This does not establish causal depth/reuse effects, broad agent capability, held-out generalization, unrestricted abstraction discovery or a Dafny-versus-Verus performance difference.

Positive integration fixtures are explicitly synthetic and default-rejected. The test helper stays outside production protocol inputs. No model request, native verifier call, execution handler or model acceptance is created by these checks.

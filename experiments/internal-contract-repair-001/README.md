The host selects each task's required new internal API before generation. The
new starting workspace keeps that contract but retains both old implementations.
The intended fresh verifier gate is an actual failure of **both** `Helper.Transfer`
and `Client.Target`. Existing one-sided and paired controls reuse exact previously
reviewed source/evidence; they are not independent new checks.

The future model may replace the two method bodies. Public client contracts,
target helper contracts, signatures, imports, result types, kernel definitions
and the include host remain fixed. This is implementation repair under a specified
API migration, not model-designed contract synthesis. The new method policy and
two-method measurement scope must be validated separately from the earlier
lemma-body handler.

The old implementations can still preserve their original end-to-end runtime
behavior. The new failure is that they do not implement the required changed
internal API, and the old caller cannot prove its obligation using that API.
This is a deliberate migration target, not a discovered public runtime bug.

Both arms receive identical full source, editable spans, syntax guidance,
settings and per-response budget. Their only intended difference is the saved
verifier diagnostic block. Reference implementations, seeded-fault labels,
counterexamples and analyst repair advice are excluded. The 16-slot order is
counterbalanced: every four-slot block contains all four task/condition cells,
and every cell has mean position 8.5. Responses use independent contexts, not
paired random seeds. Each trial receives one initial feedback block and one
response; there is no feedback after that repair or iterative agent loop.
The source, policy, named-verification and prompt-preparation gates have passed.

Strict whole-workspace verification is primary. Local helper/client outcomes,
changed bodies and observed `H.Transfer` calls are reported separately. A local
client pass under an unproved helper contract is not repository success.
Transparent kernel functions permit direct caller implementations that bypass
`H.Transfer`; these are valid if they satisfy the same contracts and edit policy.
Neither call presence nor a whole-workspace pass alone establishes necessary
helper reuse or a particular reasoning path.

These two known-family seeds cannot establish broad agent capability, a causal
depth/sharing effect or held-out performance. All earlier sources, freezes and
model scores are preserved. The tree and transition reservations remain untouched.
